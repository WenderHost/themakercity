# Maker Profile Editor: Gallery Upload Issue

**Date:** 2026-08-05

## Incident Report

For months now, users have been having trouble uploading images to their profiles. Reports came in sporadically through emails and support requests, usually describing the "Add to gallery" button on the profile editor as unresponsive or simply not working, but I was never able to reproduce the issue myself no matter what browser or device I tried. Back in February I pushed out what I thought was a fix after finding a setting that was preventing uploads for everyone, and again in April I patched what I believed was a script-loading issue, but reports kept trickling in afterward, which told me I hadn't actually found the root cause either time. To try to get better data from affected users, I added a "Share Your System Info" button to the profile editor's FAQ section so people could send me their browser, OS, and screen resolution with one click, but even with reports in hand I couldn't connect any of that information to an actual explanation for what was going wrong.

## Analysis

I had Claude do a deep audit of the profile editor page and its underlying code, and it turned up three real, confirmed issues, none of which were the FilePond-related theory I had been chasing.

The most significant one traced back to a fix I wrote myself in September 2024. I had discovered that ACF Extended Pro's JavaScript conflicts with ACF Pro's native Gallery field on the frontend, specifically by overriding the Gallery field's "add image" and "edit attachment" behavior without preserving a reference to the original methods, which breaks the "Add to gallery" button. My fix at the time deactivated ACF Extended Pro specifically on the profile editor page. In February 2025 I renamed that page's route from `/profile/` to `/profile-editor/` and updated the slug in six different files, but I missed the one file containing this fix, which silently broke the condition that gated it. From that point on, ACF Extended Pro's conflicting script loaded on every visit to the profile editor without me realizing it, which explains why the July and April patches didn't hold: I was fixing symptoms without ever addressing the actual conflict. On top of that, my original fix used `deactivate_plugins()`, which isn't scoped to a single request, so even when it was working correctly it was deactivating the plugin site-wide rather than just for that one page.

The second issue was in the code that grants the `upload_files` capability to Maker and Subscriber accounts, which is required to use the media uploader at all. The `init` hook that runs this function had been commented out, and the commented-out line even referenced a function name that no longer existed in the codebase. It had only been working because I must have patched the capability into the roles table manually through a role-editor plugin at some point in the past. Nothing in the code guaranteed that capability would stay in place, which means any role reset, migration, or plugin change could have silently broken uploads for a subset of users going forward with no way to recover automatically.

The third issue was really a diagnostic gap rather than a bug: the "Share Your System Info" feature I built only ever captured generic browser, OS, and screen resolution data. None of those fields could distinguish a missing capability from a JavaScript conflict from a rejected file upload, which is exactly why the reports I'd been collecting never actually helped me pin down what was happening.

## Fixes

I replaced the broken, site-wide plugin deactivation with a request-scoped fix that dequeues just the specific ACF Extended Pro script responsible for the conflict, gated correctly on the profile editor route this time. I fixed the capability grant so it runs automatically on every request instead of depending on a manual database patch that could disappear at any time. I also built out real logging so I'm not flying blind if this happens again: every profile save now logs the resulting gallery image count and relevant diagnostic flags, the system-info handler now logs every report and every failed email server-side instead of only showing a vague error to the user, and I added a client-side watchdog script that automatically detects and reports three concrete failure modes on its own, without anyone needing to notice something's wrong and click a button: the "Add to gallery" button being clicked with no upload modal appearing, an upload request actually failing or being rejected by WordPress (captured along with the real WordPress error text), and JavaScript errors occurring while a user is interacting with the gallery field. All of this has been deployed to production, and I've updated the FAQ note on the profile editor page to let users know I believe this is resolved and to share their system info if they still run into trouble.
